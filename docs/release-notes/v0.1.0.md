# FlightTrace v0.1.0

FlightTrace helps PX4/ArduPilot developers understand *why* autonomous
missions fail. It records MAVLink telemetry (or a deterministic demo
run), normalises it into a mission timeline, evaluates a YAML
assertion spec against the run, and produces a structured failure
report with cited evidence — locally, in one process, on your machine.

**Read-only on the vehicle by construction.** The `flighttrace-mavlink`
crate exposes no send function and an in-tree integration test greps
the source on every build to keep it that way. FlightTrace never arms,
never takes off, never changes modes, never uploads missions, never
sends any command.

## What works in v0.1.0

- **Deterministic demo** — `POST /api/demo/run` produces a synthetic
  `TAKEOFF_TIMEOUT` mission with normalized events, telemetry samples,
  assertions, and a structured failure report. No PX4 or ArduPilot
  install required.
- **MAVLink UDP ingestion** — read-only. Sessions auto-close on
  inactivity; on close, the YAML mission spec is evaluated and a
  `FailureReport` is generated when appropriate.
- **YAML assertion engine** with the v0.1 check set: `heartbeat_within_sec`,
  `armed`, `altitude_at_least_m`, `mode_not_changes`,
  `no_telemetry_gap_longer_than_sec`.
- **HTTP API** (Axum) with the documented endpoints under `/api/` plus
  `/health`. Same-origin fetches; unknown API paths return the standard
  JSON 404 envelope.
- **React + TypeScript + Vite UI** with a dark developer-debugger
  theme: runs list, run detail with a failure summary card, altitude
  chart with target/failure/statustext markers, vertical-speed
  summary, mission timeline with relative timestamps, assertion
  results table, raw event log.
- **SQLite persistence** — one file on disk, forward-compatible across
  patch releases. Back up before upgrading.

## How to run

### Fastest — extract and go

Unzip / untar the release archive, then run the binary bare:

```
# Linux / macOS
./flighttrace

# Windows — double-click start-flighttrace.bat, or:
.\flighttrace.exe
```

It auto-detects `web-dist/` next to the binary, binds a random
loopback port, prints `FlightTrace UI: http://127.0.0.1:<port>/`, and
opens the default browser.

The three developer-oriented modes below still work exactly as before
and are what you want if you're building from source.

### Developer modes

### CLI, API-only

Backend dev, `curl`-driven exploration.

```bash
cargo run -p flighttrace-cli -- serve \
    --bind 127.0.0.1:8080 \
    --database ./data/flighttrace.db
```

Then in a second terminal:

```bash
cd web && npm ci && npm run dev
```

Open <http://localhost:5173>.

### CLI, packaged web (one process)

Fastest way to see the UI in a browser without a separate dev server.

```bash
cd web && npm ci && npm run build && cd ..
cargo run -p flighttrace-cli -- serve \
    --bind 127.0.0.1:8080 \
    --database ./data/flighttrace.db \
    --web-dir ./web/dist \
    --open
```

Open <http://127.0.0.1:8080>.

### Desktop (Tauri v2)

Same UI, native window, no separate browser.

```bash
cd web && npm ci && npm run build && cd ..
cargo install tauri-cli --version '^2'
cd apps/flighttrace-desktop/src-tauri && cargo tauri dev
```

On Linux you'll need the webkit2gtk / GTK / glib development packages;
the README has a Debian/Ubuntu, Fedora, and Arch one-liner.

## Verify a packaged tree

The repo ships a smoke script that boots the binary against a
prebuilt frontend on a random loopback port and verifies the golden
endpoints:

```bash
scripts/release-smoke.sh                     # dev-local layout
scripts/release-smoke.sh --pkg-dir dist/foo  # explicit archive tree
```

## Limitations

- **No auto-bundled Tauri installer.** `cargo tauri build` produces
  installers but is not part of CI in v0.1. `web/dist` is bundled next
  to the desktop binary via `bundle.resources`; users who move the
  binary elsewhere must set `FLIGHTTRACE_WEB_DIR` or drop `web-dist/`
  next to the executable.
- **No live UI streaming.** MAVLink-sourced runs update on page
  refresh — SSE / WebSocket streaming is out of scope for v0.1.
- **Single-vehicle sessions.** Multi-vehicle keyed on MAVLink
  `system_id` is not implemented yet.
- **No `.bin` / `.ulg` log import.** Post-flight log replay is
  post-v0.1.
- **No auth, no cloud, no fleet management.** Explicitly out of scope
  and not planned — see the "What FlightTrace is not" list in the
  README.

## Safety guarantee

FlightTrace is a **passive observer** on the MAVLink socket. It does
not arm, disarm, take off, land, upload missions, set parameters, or
send any command. The `flighttrace-mavlink` crate exposes no send
function; the integration test
`crates/flighttrace-mavlink/tests/read_only_invariant.rs` greps the
crate source for forbidden send-related APIs on every build, and the
sentinel comments in `lib.rs` + `listener.rs` are asserted present.
Attach FlightTrace to a live vehicle as an observer only.

## Compatibility

- **Rust**: stable toolchain, edition 2024, MSRV ≥ 1.85.
- **Node.js**: ≥ 18 for the web UI (Vite 5).
- **Storage**: SQLite file backups recommended before upgrading.
- **HTTP API**: no breaking changes expected across v0.1.x.
